# แปะแพตช์ไฟล์ต้นฉบับเกิน ~2GB ได้ (เช่น ISO ของ PS2) ผ่าน BigBuffer

หลังแก้ `/tools/sha1` ให้อ่านไฟล์ทีละก้อนแล้ว (ADR-014/015) ยังเหลือปัญหาเดิมอยู่ที่**หน้าแปะ
แพตช์จริง** — ตรวจโค้ด `applyPPF` พบว่าบรรทัดแรกสุดคือ `new Uint8Array(source)` (สร้างสำเนา
ไฟล์ทั้งไฟล์เป็นก้อนเดียว) ชนเพดาน ~2GB ของ ArrayBuffer เหมือนกันทุกประการ — พังตั้งแต่ก้าวแรก
ก่อนเริ่มแปะด้วยซ้ำ และเป็นแบบนี้ทั้ง IPS/BPS/PPF เพราะทั้ง 3 รูปแบบเขียนทับข้อมูลตามตำแหน่ง
ต่างๆ ทั่วทั้งไฟล์ (ต่างจาก SHA-1 ที่แค่ไล่อ่านผ่านทีละไบต์) จึงต้องมีไฟล์ทั้งก้อนให้เข้าถึงแบบ
สุ่มตำแหน่ง (random access) ได้จริง แก้แบบเดียวกับ SHA-1 (อ่านทีละก้อนแล้วทิ้ง) ไม่ได้ตรงๆ

## การตัดสินใจ

เพิ่มชั้นข้อมูลใหม่ `BigBuffer` (`src/patcher/big-buffer.js`) แทน `Uint8Array` ตรงๆ — เก็บข้อมูล
โดยแบ่งเป็นหลาย segment (Uint8Array ย่อยๆ ค่าเริ่มต้น 512MB ต่อก้อน) แทนที่จะเป็น ArrayBuffer
เดียว รองรับอ่าน/เขียน/เติมค่า/คัดลอกภายในตัวเอง/ขยาย/ตัดสั้น แบบข้าม segment ได้โปร่งใส
เหมือนใช้ Uint8Array ก้อนเดียวอยู่ — ตัวแปะแพตช์ทั้ง 3 รูปแบบ (`ips.js`/`bps.js`/`ppf.js`) และ
`crc32.js` (ที่ BPS ใช้ตรวจ checksum) แก้ให้ทำงานผ่าน BigBuffer แทน

**PPF/IPS เขียนทับ `source` ตรงๆ ไม่ clone ก่อน:** เดิมทำ `out = new Uint8Array(source)`
(สำเนาเต็ม) แล้วค่อยเขียนทับ ตอนแรกย้ายมาเป็น `out = source.clone()` (สำเนา BigBuffer เต็ม
เหมือนกัน) แต่พบว่าไม่จำเป็น — ตัว `source` BigBuffer ที่ `patch-ui.js` สร้างขึ้นด้วย
`BigBuffer.fromBlob()` ถูกสร้างมาเพื่อแปะแพตช์ครั้งนี้ครั้งเดียวโดยเฉพาะ ไม่มีใครต้องใช้ค่าดิบ
ก่อนแปะต่ออีก จึงเปลี่ยนให้ `applyIPS`/`applyPPF` **เขียนทับ `source` ที่รับมาตรงๆ แล้วคืนตัวมัน
เอง** (ผู้เรียกห้ามใช้ `source` เดิมต่อหลังเรียก) ตัดขั้นตอน clone ทิ้งไปเลย

**แต่ยังกินแรมพีคใกล้ 2 เท่าอยู่ดี ตอนสร้าง Blob ผลลัพธ์:** ทดสอบจริงกับไฟล์ Resident Evil 4
(PS2) ขนาด 4.1GB วัด RSS พีคได้ ~8.3GB (~1.9 เท่าของขนาดไฟล์) เพราะ `BigBuffer.toBlob()`
(`new Blob(segments)`) เป็นก้อนข้อมูลใหม่ที่คัดลอกไบต์จาก segment เดิมเข้าไปเก็บเอง (สเปกของ
`Blob` กำหนดให้คัดลอกเนื้อหาตอนสร้างเสมอ ไม่ใช่ยืม reference) การตัด clone() ออกจาก
IPS/PPF จึงช่วยลดพีคจากขั้น "เขียนทับ" ได้จริง แต่พีครวมทั้งกระบวนการยังใกล้เคียงเดิม เพราะ
ขั้น "สร้าง Blob ให้ดาวน์โหลด" ที่ตามมาคัดลอกอีกรอบอยู่ดี — เตือนผู้ใช้เรื่องแรมไว้ตามความ
เป็นจริงที่วัดได้ ไม่ใช่ตัวเลขทฤษฎีที่คำนวณเอง

**BPS ยังกินแรมพีค ~2 เท่าอยู่** เพราะประกอบไฟล์ผลลัพธ์ขึ้นใหม่ทั้งก้อนต่างหากจาก source (ไม่ใช่
แค่เขียนทับ) — ต้องมีทั้งต้นฉบับและผลลัพธ์อยู่พร้อมกันตลอด ไม่มีทางเลี่ยงง่ายๆ เพราะ `TargetCopy`
อ้างอิงตำแหน่งใดๆ ในผลลัพธ์ที่เขียนไปแล้วก็ได้ (ไม่มีขอบเขตที่รับประกันได้ว่า "ใกล้ๆ" เท่านั้น) —
แต่ PS2 (เป้าหมายหลักของงานนี้) แจกแพตช์กันเป็น PPF เกือบทั้งหมดอยู่แล้ว (ตามชื่อฟอร์แมตเลย —
"PS1/PS2 patch format") จึงไม่ใช่เส้นทางที่ใช้จริงบ่อย ยังต้องเตือนผู้ใช้ให้ปิดโปรแกรม/แท็บอื่น
ก่อนแปะไฟล์ใหญ่มากๆ อยู่ดี (ไฟล์ 4GB ก็ยังใช้แรมหลัก GB อยู่ ต่อให้ลดจาก ~8GB เหลือ ~4-5GB แล้ว)

**BPS กินแรมกว่า IPS/PPF สำหรับไฟล์ขนาดเดียวกันเสมอ** เพราะประกอบไฟล์ผลลัพธ์ขึ้นใหม่ทั้งก้อน
(ไม่ใช่แค่เขียนทับสำเนาต้นฉบับ) ต้องถือทั้งต้นฉบับและผลลัพธ์พร้อมกันตลอด ไม่มีทางเลี่ยงง่ายๆ
เพราะ `TargetCopy` อ้างอิงตำแหน่งใดๆ ในผลลัพธ์ที่เขียนไปแล้วก็ได้ (ไม่มีขอบเขตที่รับประกันได้ว่า
"ใกล้ๆ" เท่านั้น) — แต่ PS2 (เป้าหมายหลักของงานนี้) แจกแพตช์กันเป็น PPF เกือบทั้งหมดอยู่แล้ว
(ตามชื่อฟอร์แมตเลย — "PS1/PS2 patch format") จึงไม่ใช่เส้นทางที่ใช้จริงบ่อย

## ไฟล์ผลลัพธ์ (ที่อาจใหญ่กว่า 2GB เท่ากัน) ดาวน์โหลดออกมายังไง

`BigBuffer.toBlob()` สร้าง `new Blob(segments)` จาก array ของ segment ตรงๆ **ไม่รวมเป็น
ArrayBuffer เดียวก่อน** — เอกสารของ Chrome ยืนยันว่า Blob/File เก็บข้อมูลได้มากกว่าที่แรมมี
โดยล้นไปเก็บที่ดิสก์ชั่วคราวเอง (ไม่ผูกกับเพดาน ArrayBuffer ~2GB)

**ทดสอบยืนยันแล้วด้วยไฟล์จริงระดับ 4GB+:** รันทั้งกระบวนการจริง (`BigBuffer` จากไฟล์ →
`applyPPF` → `toBlob()`) กับไฟล์ ISO ของ Resident Evil 4 (PS2) ขนาด 4,435,836,928 ไบต์
(~4.13GB) และไฟล์แพตช์ `RE4_Thai.ppf` จริงที่จะแจกบนเว็บ — **ผลลัพธ์ตรงกับค่า MD5 ที่ผู้แปล
ยืนยันไว้เป๊ะ** (`b42d9be68694edbd01cca92e19cb2863`) ยืนยันว่าโค้ดที่ deploy จริงถูกต้องแม้ที่
ขนาดไฟล์เกิน 4GB (ผ่านเพดาน 2^32 ไบต์ไปแล้ว ไม่ใช่แค่เพดาน ~2GB ของ ArrayBuffer เดิม)

**เจอบั๊กของ Node (ไม่ใช่ของเรา) ระหว่างทดสอบ แต่ไม่กระทบโค้ดจริง:** ตอนพยายามอ่าน Blob
ผลลัพธ์กลับด้วย `.slice()` เพื่อตรวจซ้ำ Node.js (ที่รันเทสนี้) ล่มด้วย native assertion
(`node_blob.cc`, "args[1]->IsUint32()") ทันทีที่ `slice()` ได้ค่า offset เกิน 2^32 (4.29GB) —
เป็นข้อจำกัดของ Node.js เอง ไม่เกี่ยวกับเบราว์เซอร์ และที่สำคัญคือ **โค้ดที่ deploy จริงไม่เคย
เรียก `.slice()` กับ Blob ผลลัพธ์เลย** — `patch-ui.js` แค่ `URL.createObjectURL()` แล้วกดดาวน์โหลด
ผ่าน `<a download>` ตรงๆ ไม่ผ่าน `.slice()` จึงไม่ชนบั๊กนี้ (แก้ปัญหาในการทดสอบเองด้วยการอ่านค่า
MD5 จาก `result.segments` ตรงๆ แทน)

**สิ่งที่ยังไม่ได้ยืนยันจากตรงนี้:** การดาวน์โหลด Blob ขนาด 4GB+ จริงผ่าน `<a download>` ใน
เบราว์เซอร์จริง (Node ไม่มี `<a>`/DOM ให้ทดสอบส่วนนี้) — ควรจะทำงานได้ปกติเพราะเป็นกลไก
มาตรฐานที่เบราว์เซอร์ใช้ดาวน์โหลดไฟล์ใหญ่อยู่แล้ว (เหมือนดาวน์โหลดไฟล์ .iso ทั่วไป) แต่ยังไม่มี
การทดสอบตรงจากสภาพแวดล้อมนี้ — จุดนี้เจ้าของเว็บควรลองกดดาวน์โหลดจริงดูสักครั้ง

## ผลกระทบอื่น

- `patch-ui.js`: เลิกอ่านไฟล์ต้นฉบับทั้งไฟล์ตอนเลือกไฟล์ (`file.arrayBuffer()`) — เช็คไฟล์บีบอัด
  ด้วย magic bytes 4 ไบต์แรกพอ (ไม่ต้องอ่านทั้งไฟล์) ส่วนเช็ค SHA1 (ถ้าเกมตั้งไว้) ใช้
  `sha1HexOfBlob` (ADR-015) แทน — ไฟล์ต้นฉบับเต็มจะถูกอ่านเข้า BigBuffer อีกทีตอนกดปุ่มแปะจริง
  (ไม่ค้างอยู่ในหน่วยความจำระหว่างที่ผู้ใช้ยังไม่กดปุ่ม)
- เพิ่มคำเตือนเรื่องแรมสำหรับไฟล์ที่ใหญ่กว่า 1.5GB โดยเฉพาะ (แยกจากคำเตือน "ไฟล์ใหญ่ทั่วไป" เดิม
  ที่ 300MB) แนะนำให้ปิดแท็บ/โปรแกรมอื่นและใช้คอมพิวเตอร์แทนมือถือ
- เทส: `big-buffer.test.js` ตรวจทุกเมธอดของ BigBuffer โดยตรง (อ่าน/เขียน/เติมค่า/คัดลอกในตัวเอง/
  ขยาย/ตัดสั้น/clone/fromBlob/toBlob) และ `patcher.test.js` รันทุกเทสเดิมซ้ำที่หลายขนาด segment
  (ก้อนเดียวใหญ่ + segment เล็กจิ๋ว 1-3 ไบต์) เพื่อพิสูจน์ตรรกะข้าม segment ถูกต้องจริง ไม่ใช่ผ่าน
  เพราะข้อมูลทดสอบเล็กจนอยู่ segment เดียวพอดี

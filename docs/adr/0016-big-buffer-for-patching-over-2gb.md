# แปะแพตช์ไฟล์ต้นฉบับเกิน ~2GB ได้ (เช่น ISO ของ PS2) ผ่าน BigBuffer

หลังแก้ `/tools/sha1` ให้อ่านไฟล์ทีละก้อนแล้ว (ADR-014/015) ยังเหลือปัญหาเดิมอยู่ที่**หน้าแปะ
แพตช์จริง** — ตรวจโค้ด `applyPPF` พบว่าบรรทัดแรกสุดคือ `new Uint8Array(source)` (สร้างสำเนา
ไฟล์ทั้งไฟล์เป็นก้อนเดียว) ชนเพดาน ~2GB ของ ArrayBuffer เหมือนกันทุกประการ — พังตั้งแต่ก้าวแรก
ก่อนเริ่มแปะด้วยซ้ำ และเป็นแบบนี้ทั้ง IPS/BPS/PPF เพราะทั้ง 3 รูปแบบเขียนทับข้อมูลตามตำแหน่ง
ต่างๆ ทั่วทั้งไฟล์ (ต่างจาก SHA-1 ที่แค่ไล่อ่านผ่านทีละไบต์) จึงต้องมีไฟล์ทั้งก้อนให้เข้าถึงแบบ
สุ่มตำแหน่ง (random access) ได้จริง แก้แบบเดียวกับ SHA-1 (อ่านทีละก้อนแล้วทิ้ง) ไม่ได้ตรงๆ

## การตัดสินใจ

เพิ่มชั้นข้อมูลใหม่ `BigBuffer` (`src/patcher/big-buffer.js`) แทน `Uint8Array` ตรงๆ — เก็บข้อมูล
โดยแบ่งเป็นหลาย segment (Uint8Array ย่อยๆ ค่าเริ่มต้น 512MB ต่อก้อน) แทนที่จะเป็น ArrayBuffer
เดียว รองรับอ่าน/เขียน/เติมค่า/คัดลอกภายในตัวเอง/ขยาย/ตัดสั้น แบบข้าม segment ได้โปร่งใส
เหมือนใช้ Uint8Array ก้อนเดียวอยู่ — ตัวแปะแพตช์ทั้ง 3 รูปแบบ (`ips.js`/`bps.js`/`ppf.js`) และ
`crc32.js` (ที่ BPS ใช้ตรวจ checksum) แก้ให้ทำงานผ่าน BigBuffer แทน

**เหตุผลที่ยังไม่ทำ copy-on-write:** PPF/IPS เดิมทำ `out = new Uint8Array(source)` (สำเนาเต็ม)
แล้วค่อยเขียนทับ — ทำแบบเดิมต่อไป (`source.clone()` สำเนาทุก segment เต็ม) แทนที่จะแชร์ segment
ที่ยังไม่ถูกแก้ (ซึ่งจะประหยัดแรมกว่ามากถ้าแพตช์แก้แค่บางจุด) เพราะการทำ copy-on-write ต้องมี
ตรรกะ "clone segment ตอนเขียนทับครั้งแรกเท่านั้น" แทรกอยู่ทุกจุดที่เขียน เพิ่มความเสี่ยงบั๊กใน
โค้ดที่พังแล้วทำไฟล์เกมเสียได้ — เลือกความถูกต้องที่พิสูจน์ง่ายกว่าไว้ก่อนสำหรับรอบแรกนี้
**ผลคือแรมที่ต้องใช้พีคสูงสุดประมาณ 2 เท่าของขนาดไฟล์ต้นฉบับชั่วขณะตอน clone()** (เช่น ไฟล์
4GB ใช้แรมพีคได้ถึง ~8GB) — ต้องเตือนผู้ใช้ให้ปิดโปรแกรม/แท็บอื่นก่อนแปะไฟล์ใหญ่มากๆ

**BPS กินแรมกว่า IPS/PPF สำหรับไฟล์ขนาดเดียวกันเสมอ** เพราะประกอบไฟล์ผลลัพธ์ขึ้นใหม่ทั้งก้อน
(ไม่ใช่แค่เขียนทับสำเนาต้นฉบับ) ต้องถือทั้งต้นฉบับและผลลัพธ์พร้อมกันตลอด ไม่มีทางเลี่ยงง่ายๆ
เพราะ `TargetCopy` อ้างอิงตำแหน่งใดๆ ในผลลัพธ์ที่เขียนไปแล้วก็ได้ (ไม่มีขอบเขตที่รับประกันได้ว่า
"ใกล้ๆ" เท่านั้น) — แต่ PS2 (เป้าหมายหลักของงานนี้) แจกแพตช์กันเป็น PPF เกือบทั้งหมดอยู่แล้ว
(ตามชื่อฟอร์แมตเลย — "PS1/PS2 patch format") จึงไม่ใช่เส้นทางที่ใช้จริงบ่อย

## ไฟล์ผลลัพธ์ (ที่อาจใหญ่กว่า 2GB เท่ากัน) ดาวน์โหลดออกมายังไง

`BigBuffer.toBlob()` สร้าง `new Blob(segments)` จาก array ของ segment ตรงๆ **ไม่รวมเป็น
ArrayBuffer เดียวก่อน** — เอกสารของ Chrome ยืนยันว่า Blob/File เก็บข้อมูลได้มากกว่าที่แรมมี
โดยล้นไปเก็บที่ดิสก์ชั่วคราวเอง (ไม่ผูกกับเพดาน ArrayBuffer ~2GB) ทดสอบยืนยันแล้วจริงในเบราว์เซอร์
จริง (ไม่ใช่แค่ Node) ที่ 900MB (patch 3 จุดกระจายทั่วไฟล์ อ่านกลับด้วย `.slice().arrayBuffer()`
ได้ค่าตรงทุกจุด) — แต่**ยังทดสอบไม่ถึงระดับ 4GB+ จริงจากสภาพแวดล้อมนี้ได้** (ตัวทดสอบอัตโนมัติ
เจอ `NotReadableError` ตอนสร้าง Blob รวม ~1.8GB ขึ้นไปในคอนเทนเนอร์ทดสอบเอง ซึ่งน่าจะเป็น
ข้อจำกัดเรื่องพื้นที่ดิสก์ของคอนเทนเนอร์นั้นเอง ไม่ใช่เพดานจริงของ Chrome ทั่วไป — แต่ยืนยัน
100% จากตรงนี้ไม่ได้) **จึงต้องให้เจ้าของเว็บทดสอบไฟล์จริงขนาด 4GB+ บนเครื่องตัวเองอีกที**
ก่อนเชื่อว่าใช้ได้จริงเต็มร้อย

## ผลกระทบอื่น

- `patch-ui.js`: เลิกอ่านไฟล์ต้นฉบับทั้งไฟล์ตอนเลือกไฟล์ (`file.arrayBuffer()`) — เช็คไฟล์บีบอัด
  ด้วย magic bytes 4 ไบต์แรกพอ (ไม่ต้องอ่านทั้งไฟล์) ส่วนเช็ค SHA1 (ถ้าเกมตั้งไว้) ใช้
  `sha1HexOfBlob` (ADR-015) แทน — ไฟล์ต้นฉบับเต็มจะถูกอ่านเข้า BigBuffer อีกทีตอนกดปุ่มแปะจริง
  (ไม่ค้างอยู่ในหน่วยความจำระหว่างที่ผู้ใช้ยังไม่กดปุ่ม)
- เพิ่มคำเตือนเรื่องแรมสำหรับไฟล์ที่ใหญ่กว่า 1.5GB โดยเฉพาะ (แยกจากคำเตือน "ไฟล์ใหญ่ทั่วไป" เดิม
  ที่ 300MB) แนะนำให้ปิดแท็บ/โปรแกรมอื่นและใช้คอมพิวเตอร์แทนมือถือ
- เทส: `big-buffer.test.js` ตรวจทุกเมธอดของ BigBuffer โดยตรง (อ่าน/เขียน/เติมค่า/คัดลอกในตัวเอง/
  ขยาย/ตัดสั้น/clone/fromBlob/toBlob) และ `patcher.test.js` รันทุกเทสเดิมซ้ำที่หลายขนาด segment
  (ก้อนเดียวใหญ่ + segment เล็กจิ๋ว 1-3 ไบต์) เพื่อพิสูจน์ตรรกะข้าม segment ถูกต้องจริง ไม่ใช่ผ่าน
  เพราะข้อมูลทดสอบเล็กจนอยู่ segment เดียวพอดี

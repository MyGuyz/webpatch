# เขียน SHA-1 เองสำรองไว้ สำหรับไฟล์ที่ใหญ่กว่า ~2GB

ผู้ใช้แจ้งว่าหน้า `/tools/sha1` ขึ้น "อ่านไฟล์ไม่สำเร็จ — ไฟล์อาจใหญ่เกินกว่าที่เครื่องจะไหว"
**ทั้งที่ใช้บนคอมพิวเตอร์** (ไม่ใช่มือถือ) ตรวจแล้วพบว่าไม่เกี่ยวกับสเปกเครื่องเลย —
`crypto.subtle.digest()` (Web Crypto API มาตรฐานที่ `sha1Hex` ใช้อยู่เดิม) มีเพดานที่ไม่มี
เอกสารเตือนชัดๆ: **ทั้ง Chrome และ Firefox ปฏิเสธ ArrayBuffer ที่ใหญ่กว่า ~2GB เสมอ** ไม่ว่า
เครื่องจะแรงหรือแรมเหลือแค่ไหนก็ตาม (ยืนยันจากปัญหาที่มีคนเจอแบบเดียวกันตอนแฮชไฟล์ >2GB —
ดู [immich-app/immich#15739](https://github.com/immich-app/immich/issues/15739)) ข้อความเดิม
จึงชี้ผู้ใช้ไปผิดทาง เพราะ "ลองบนคอมพิวเตอร์" ไม่ช่วยแก้ปัญหานี้เลย

เกม PS1 แผ่นเดียวไม่เจอปัญหานี้ (ไม่เกิน ~700MB) แต่ไฟล์ ISO ของ PS2/DVD มักใหญ่กว่า 2GB —
เว็บนี้เคยถูกถามว่ารองรับ PS2 ไหม (ดูบันทึกแชท) จึงต้องแก้จุดนี้ก่อนจะรองรับเครื่องรุ่นใหม่ได้จริง

## การตัดสินใจ

เพิ่มทางสำรอง: ถ้าไฟล์ใหญ่กว่าเพดานของ `crypto.subtle.digest` (`WEBCRYPTO_MAX_BYTES` ใน
`src/patcher/sha1.js`) ให้เปลี่ยนไปใช้ SHA-1 ที่เขียนเองตาม FIPS 180-4 แทน ประมวลผลจาก
`Uint8Array` เดิมที่โหลดไว้ในหน่วยความจำอยู่แล้วทีละบล็อก 64 ไบต์ (ไม่คัดลอกข้อมูลทั้งไฟล์ซ้ำ)
และคั่นด้วย `setTimeout` เป็นระยะกันแท็บค้างระหว่างคำนวณไฟล์หลาย GB

**ทำไมไม่ใช้ streaming API อื่น:** Web Crypto ไม่มี API ให้ป้อนข้อมูลทีละก้อน (เหมือน
`hash.update()` ของ Node) กับ `digest` เลย ตัวเลือกที่เหลือคือเขียนอัลกอริทึมเองหรือใช้ไลบรารี
ภายนอก เลือกเขียนเองเพราะ SHA-1 เป็นอัลกอริทึมสั้นและนิ่ง (ไม่มีอัปเดต) ไม่คุ้มเพิ่ม dependency
ใหม่เข้ามาทั้ง bundle สำหรับ fallback ที่ใช้แค่ไฟล์ส่วนน้อยมาก (>2GB)

**ทำไมยังคง `crypto.subtle` เป็นทางหลัก:** เร็วกว่าโค้ด JS ล้วนมาก (โค้ดเนทีฟ) ไฟล์ส่วนใหญ่
(PS1/GBA/NDS/SFC ทั้งหมด) เล็กกว่าเพดานอยู่แล้ว จึงยังได้ความเร็วเดิมสำหรับ 99% ของการใช้งาน
ทางสำรองที่ช้ากว่าจะโดนใช้เฉพาะไฟล์ขนาด GB ที่ต้องรอสักพักอยู่แล้วตามธรรมชาติ

**ทดสอบอย่างไร:** เพิ่ม `src/patcher/sha1.test.js` ตรวจทั้งสองทาง (ปกติ + สำรอง) กับค่ามาตรฐาน
FIPS 180-4 และเทียบกับ `node:crypto` (`createHash('sha1')`) ที่ทุกความยาวขอบเขตของ padding
(0, 54–57, 63–65, 119–121, 127–129 ไบต์ ฯลฯ) รวมถึงเทสระดับ ~64MB ที่ครอบจุดที่โค้ดคั่นด้วย
`setTimeout` ด้วย — ทุกจุดต้องได้ค่าตรงกับ `node:crypto` เป๊ะ เพราะ SHA-1 เพี้ยนแม้แต่บิตเดียว
จะทำให้ตรวจรุ่นไฟล์ผิด (ปฏิเสธไฟล์ถูกรุ่น หรือแย่กว่านั้นคือปล่อยไฟล์ผิดรุ่นผ่าน)

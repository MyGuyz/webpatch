# อ่านไฟล์ทีละก้อนแทนการอ่านทั้งไฟล์เป็น ArrayBuffer เดียว สำหรับไฟล์เกิน ~2GB

ผู้ใช้แจ้งว่าหน้า `/tools/sha1` ขึ้น "อ่านไฟล์ไม่สำเร็จ — ไฟล์อาจใหญ่เกินกว่าที่เครื่องจะไหว"
**ทั้งที่ใช้บนคอมพิวเตอร์** (ไม่ใช่มือถือ) ตรวจแล้วพบว่าไม่เกี่ยวกับสเปกเครื่องเลย มีเพดานที่
ไม่มีเอกสารเตือนชัดๆ ซ้อนกันอยู่ 2 ชั้น:

1. **`crypto.subtle.digest()`** (Web Crypto API มาตรฐานที่ `sha1Hex` ใช้อยู่เดิม) ปฏิเสธ
   ArrayBuffer ที่ใหญ่กว่า ~2GB เสมอ (ดูปัญหาเดียวกันที่มีคนเจอ —
   [immich-app/immich#15739](https://github.com/immich-app/immich/issues/15739))
2. **ก่อนจะถึงขั้นนั้นด้วยซ้ำ** — Chrome จำกัด ArrayBuffer ทั่วไปทุกชนิด (ไม่ใช่แค่ตัวที่ป้อนให้
   `crypto.subtle`) ไว้ที่ `0x7fe00000` ไบต์ (~2.1GB) เท่ากันโดยประมาณ — ดู
   [chromium issue 40055619](https://issues.chromium.org/issues/40055619) และ
   [bugzilla 1392234](https://bugzilla.mozilla.org/show_bug.cgi?id=1392234) (Firefox มีปัญหา
   คล้ายกัน) นี่คือของจริงที่ทำให้ผู้ใช้ยังเจอปัญหาเดิมแม้จะแก้ข้อ 1 ไปแล้วรอบแรก — เพราะ
   `file.arrayBuffer()` (เรียกกับไฟล์ทั้งไฟล์ตรงๆ) พังตั้งแต่ก้าวแรกสำหรับไฟล์ไซซ์นี้ ไม่ทันได้
   ไปถึง `crypto.subtle` เลยด้วยซ้ำ — ยืนยันจริงกับไฟล์ 4.13GB (4,435,836,928 ไบต์) ที่ผู้ใช้ทดสอบ

ทั้งสองข้อเป็นข้อจำกัดของตัวเบราว์เซอร์เอง **ไม่เกี่ยวกับแรม/สเปกเครื่องเลย** ข้อความเดิมที่บอก
"ลองบนคอมพิวเตอร์ดูนะ" จึงชี้ทางผิด สลับไปคอมแรงแค่ไหนก็ไม่ช่วย

เกมที่เป็นแผ่นเดียวอย่าง PS1 ไม่เจอปัญหานี้ (ไม่เกิน ~700MB) แต่ไฟล์ ISO ของ PS2/DVD มักใหญ่กว่า
2GB จึงต้องแก้จุดนี้ก่อนจะรองรับเครื่องรุ่นใหม่ได้จริง

## การตัดสินใจ

หยุดอ่านทั้งไฟล์เป็น ArrayBuffer เดียวโดยสิ้นเชิงสำหรับไฟล์ที่อาจใหญ่ — เปลี่ยนไปอ่านทีละก้อน
เล็กๆ (`Blob.slice()` ทีละ 64MB) แล้วป้อนเข้า SHA-1 แบบสะสมทีละก้อนแทน (`createSha1()` ใน
`src/patcher/sha1.js` คืนตัวแฮชที่มี `update(bytes)`/`digestHex()` เก็บ state ข้ามการเรียกได้)
หน้า `/tools/sha1` เรียกผ่าน `sha1HexOfBlob(file, onProgress)` ตัวใหม่ ซึ่งไม่มีจุดไหนเลยที่ต้อง
ถือทั้งไฟล์ไว้ในหน่วยความจำก้อนเดียวอีกต่อไป ไฟล์ขนาดเท่าไหร่ก็แฮชได้ (จำกัดแค่เวลารอ)

ไฟล์เล็ก (≤ ~1.9GB) ยังใช้ทางลัดผ่าน `crypto.subtle.digest` เหมือนเดิม (เร็วกว่าโค้ด JS ล้วนมาก
และครอบคลุมไฟล์ทุกเครื่องรุ่นเก่า PS1/GBA/NDS/SFC อยู่แล้ว) ทางอ่านทีละก้อนโดนใช้เฉพาะไฟล์ที่
ใหญ่กว่านี้จริงๆ

**ทำไมไม่ใช้ streaming API อื่น:** Web Crypto ไม่มี API ให้ป้อนข้อมูลทีละก้อนกับ `digest` เลย
ตัวเลือกที่เหลือคือเขียนอัลกอริทึมเองหรือใช้ไลบรารีภายนอก เลือกเขียนเองเพราะ SHA-1 เป็น
อัลกอริทึมสั้นและนิ่ง (ไม่มีอัปเดต) ไม่คุ้มเพิ่ม dependency ใหม่เข้ามาทั้ง bundle

**ข้อจำกัดที่ยังไม่แก้ (นอกขอบเขตของรอบนี้):** การ**แปะแพตช์จริง**ในหน้าแปะแพตช์
(`patch-ui.js`) ยังอ่านไฟล์ต้นฉบับทั้งไฟล์เป็น `Uint8Array` เดียวอยู่ (`new Uint8Array(await
file.arrayBuffer())`) เพราะอัลกอริทึม IPS/BPS/PPF ต้องเข้าถึงข้อมูลแบบสุ่มตำแหน่ง (random
access) ในหน่วยความจำก้อนเดียว — ไฟล์ต้นฉบับที่ใหญ่กว่า ~2GB (เช่น ISO ของ PS2) จะยังพังที่ขั้น
ตอนนี้อยู่ ต่อให้แฮชผ่าน `/tools/sha1` ได้แล้วก็ตาม การแก้จุดนี้ต้องเปลี่ยนตัวแพตช์เอนจินให้ทำงาน
แบบ chunk/stream ได้ ซึ่งเป็นงานใหญ่กว่านี้มาก ยังไม่ได้ทำในรอบนี้

**ทดสอบอย่างไร:** `src/patcher/sha1.test.js` ตรวจ `createSha1` เทียบกับ `node:crypto` ทั้งแบบ
ป้อนทีเดียวและแบ่งป้อนหลายก้อน (ขนาดก้อนต่างๆ กัน รวมถึงก้อนที่ตกกลางขอบเขต padding พอดี) และ
ตรวจ `sha1HexOfBlob` ด้วยการอ่านทีละก้อนจริงผ่าน `Blob.slice()` ขนาด >64MB (จำลองพฤติกรรมไฟล์
ใหญ่โดยไม่ต้องสร้างไฟล์ทดสอบขนาดหลาย GB จริงซึ่งช้าเกินไปสำหรับเทส) ทุกจุดต้องตรงกับ
`node:crypto` เป๊ะ เพราะ SHA-1 เพี้ยนแม้แต่บิตเดียวจะทำให้ตรวจรุ่นไฟล์ผิด

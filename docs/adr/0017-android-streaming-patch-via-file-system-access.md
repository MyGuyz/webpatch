# แปะไฟล์ใหญ่บน Android ได้ผ่าน File System Access API (สตรีมทีละก้อน)

หลังแก้ให้เว็บเตือนผู้ใช้มือถือชัดเจนก่อนแปะไฟล์ใหญ่แล้ว (ADR-016) เจ้าของเว็บถามว่ามีทางให้
มือถือแปะไฟล์ใหญ่ได้จริงไหม (ยอมรับว่าช้าลงได้) คำตอบคือ **มีทางสำหรับ Android แต่ไม่มีทางสำหรับ
iPhone** เพราะข้อจำกัดจริงไม่ใช่เรื่องความเร็ว แต่คือ**ต้องมีทั้งไฟล์ต้นฉบับ + ผลลัพธ์อยู่ในแรม
พร้อมกันก่อนจะดาวน์โหลดได้** (`BigBuffer` + `Blob` ตามที่ทำใน ADR-016) — Safari ไม่มี API ให้เขียน
ไฟล์ลงดิสก์ตรงๆ เลย ในขณะที่ Chrome/Edge บน Android (และ desktop) มี **File System Access API**
(`showSaveFilePicker` + `FileSystemWritableFileStream`) ที่เขียนผลลัพธ์ลงดิสก์**ทีละก้อนระหว่าง
คำนวณ**ได้เลย ไม่ต้องรวมเป็นก้อนเดียวในแรมก่อน

## การตัดสินใจ

ทำเฉพาะ **PPF** (ไม่ทำ IPS/BPS) เพราะ:
- PS2 (เป้าหมายหลักของงานนี้) แจกแพตช์กันเป็น PPF เกือบทั้งหมด
- PPF ไม่ขยาย/ไม่ตัดไฟล์ ขนาดผลลัพธ์เท่าต้นฉบับเป๊ะเสมอ ทำให้อ่านต้นฉบับตามลำดับตั้งแต่ต้น
  จนจบแล้วเขียนทับเป็นจุดๆ ระหว่างทางได้ตรงไปตรงมา (ไม่ต้องรู้ความยาวผลลัพธ์ล่วงหน้าหรือสุ่ม
  อ่านแบบ BPS)
- IPS/BPS ใช้กับ ROM เล็ก (SNES/GBA) ที่ไม่เจอปัญหาแรมอยู่แล้ว ไม่คุ้มเพิ่มความซับซ้อน

**สถาปัตยกรรม:**
- `src/patcher/ppf.js` แยก `parsePPFRecords()` (แกะ header + เรคคอร์ด) ออกจาก `applyPPF()`
  (เขียนทับ BigBuffer) — ตัวแกะนี้ใช้ร่วมกันทั้งทาง BigBuffer เดิมและทางสตรีมใหม่ กันตรรกะ
  แกะไฟล์ PPF ที่มีรายละเอียดปลีกย่อยเยอะ (3 เวอร์ชัน, undo data, @BEGIN_FILE_ID.DIZ) เพี้ยน
  ไปคนละแบบระหว่างสองทาง
- `src/patcher/stream-ppf.js` — `streamApplyPPF(sourceFile, patch, writable, onProgress,
  chunkBytes)` อ่านไฟล์ต้นฉบับทีละก้อน (ค่าเริ่มต้น 16MB) เขียนทับเรคคอร์ดที่ overlap ช่วงนั้น
  แล้วส่งก้อนออกให้ `writable` ทันที ใช้ "sliding window" ไล่เรคคอร์ดที่เรียงตาม offset ไว้แล้ว
  (ไม่ใช่ cursor ตัวเดียว — เทสจับได้ว่า cursor เดี่ยวพังตอนมีเรคคอร์ดที่ offset ชนกันเอง แม้จะ
  ไม่ใช่แพตช์จริงที่เกิดขึ้นได้ ก็แก้ให้ถูกไว้เพื่อความทนทาน)
- `src/lib/save-file-stream.js` — ห่อ `showSaveFilePicker()` ไว้ที่เดียว คืนทั้ง `handle`
  (เอา `.name` จริงไปโชว์ในคู่มือเปิดเล่น) กับ `writable`

**เงื่อนไขที่ใช้ทางนี้ (`patch-ui.js`):** `isMobileDevice() && ขนาดไฟล์ > 1GB &&
patch_format === 'ppf' && supportsStreamingSave()` — จำกัดเฉพาะกรณีที่จำเป็นจริงๆ เท่านั้น
เดสก์ท็อปยังใช้ทาง BigBuffer เดิมเสมอ (ทดสอบแล้วใช้งานได้ดีอยู่แล้วที่ ADR-016 ไม่มีเหตุผลต้อง
เปลี่ยน UX ที่ทำงานอยู่แล้ว) ไฟล์เล็กก็ยังใช้ทางเดิม (ไม่ต้องเจอกล่อง "เลือกที่เก็บไฟล์" เพิ่มโดย
ไม่จำเป็น)

**ผลกระทบต่อ UX:** ทางสตรีมต้อง**เลือกที่เก็บไฟล์ก่อนเริ่มแปะ** (กล่องคล้าย "Save As") ต่างจาก
ทางเดิมที่ดาวน์โหลดอัตโนมัติเข้าโฟลเดอร์ Downloads หลังแปะเสร็จ — ขั้นตอนนี้เลี่ยงไม่ได้เพราะเป็น
ข้อบังคับของตัว API เอง (ต้องรู้ปลายทางก่อนเริ่มเขียนทีละก้อน) ป๊อปอัปคู่มือเปิดเล่นหลังแปะเสร็จ
ปรับข้อความ STAGE 1 ให้ตรงกับทางที่ใช้ (`patch-done-stage1-text`)

## ทดสอบอย่างไร

- `stream-ppf.test.js`: เทียบผลลัพธ์กับ `applyPPF` (ทางเดิม ที่มีเทสของตัวเองอยู่แล้ว) ที่ขนาด
  chunk หลายแบบ (1 ไบต์ไปจนถึงเกินไฟล์ทั้งก้อน) รวมเทสเฉพาะกรณีเรคคอร์ดคร่อมรอยต่อก้อนพอดี
  และเรคคอร์ด overlap กันเอง (เจอบั๊กจริงจากเทสนี้ระหว่างพัฒนา — cursor ตัวเดียวพลาดกรณีนี้
  แก้เป็น sliding window แล้ว) และเทสไฟล์ระดับ 20MB จริงพร้อมเรคคอร์ด 500 รายการ
- **ทดสอบกับไฟล์จริงระดับ 4GB+:** รัน `streamApplyPPF` กับ ISO ของ Resident Evil 4 (PS2)
  4.13GB จริง + แพตช์ `RE4_Thai.ppf` จริง ใช้ `writable` จำลองที่ไม่เก็บอะไรไว้เลย (แค่แฮช MD5
  สะสม) — **ได้ MD5 ตรงกับผลลัพธ์ที่ยืนยันไว้เป๊ะ** และ **RSS พีคแค่ ~90MB** ตลอดกระบวนการ
  (เทียบกับทาง BigBuffer เดิมที่วัดได้ ~8.3GB สำหรับไฟล์ขนาดเดียวกัน — ดู ADR-016) ยืนยันชัดว่า
  ทางสตรีมนี้แก้ปัญหาแรมได้จริงตามที่ออกแบบไว้
- **ยังไม่ได้ทดสอบ:** การกดผ่านกล่อง `showSaveFilePicker()` จริงบนอุปกรณ์ Android จริง (ทดสอบ
  อัตโนมัติทำไม่ได้เพราะต้องมี user gesture และกล่องเป็นระดับ OS) เจ้าของเว็บควรลองแปะไฟล์ใหญ่
  จริงบน Android เครื่องจริงอีกทีก่อนเชื่อว่าใช้ได้เต็มร้อย
